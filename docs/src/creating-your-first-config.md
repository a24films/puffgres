# Creating Your First Config

The basic unit of puffgres is a **config**, which defines a mapping between a Postgres table and a turbopuffer namespace. Run `puffgres new` to run the interactive wizard / generate the relevant files.

The timestamp ensures configs are applied in creation order, like database migrations. Configs are immutable — both the config and transform are content-hashed in Postgres state.  Puffgres will fail to run if the config or transform has changed after being applied; the idea here is we don't want a turbopuffer namespace to contain rows produced by two differnt versions of a transform. If you need to change how a config works, tombstone the old one and create a new one (see [Applying](#applying)) for more. 

## Configs

`config.toml` defines the source table and destination namespace:

```toml
name = "film"
namespace = "internal_film_title"

[source]
table = "internal_film"

[id]
column = "id"
type = "string"
```

### Fields

- **`name`** — identifier for this config.
- **`namespace`** — the destination turbopuffer namespace. Must be unique across all configs; puffgres will error if two configs target the same namespace.
- **`source.table`** — the Postgres table to replicate. (Only the `public` schema is supported today, so there's no schema to set.)
- **`id.column`** — the column used as the primary identifier. Must be a single column — composite keys are not supported.
- **`id.type`** — the type of the id column. One of: `uint`, `int`, `uuid`, `string`.


## Schema

`schema.ts` is auto-generated on creation or re-generated with `puffgres generate`; both read the Postghres table and produced typed column definitions. This is supposed to be autogenerated and because transforms rely on it, you need to update it if you do migrations on your upstream Postgres database. Puffgres (correctly!) will fail on a non-autogenerated file. 

```typescript
// Auto-generated by `puffgres generate`. Do not edit.
// Source: public.smart_buyer

import { parseRow as parseRowInternal, parseRows as parseRowsInternal, type Column } from "../../utils/puffgres";

export const columns = [
  { name: "id", type: "string" },
  { name: "buyer_name", type: "string" },
  { name: "buyer_id", type: "string" },
] as const satisfies readonly Column[];

export const parseRow = (cols: (string | null)[]) => parseRowInternal(columns, cols);
export const parseRows = (rows: (string | null)[][]) => parseRowsInternal(columns, rows);
```

You can use the generated `parseRow` function in your configs to coerce Postgres strings into relevant TS types. 

## Transforms

Transforms are a long-lived TypeScript processes that communicates with puffgres over stdin/stdout using JSONL (newline-delimited JSON). You define them in a `transform.ts` file. They are meant to be maximally expressive; templates are just starting points. We use these internally to embed, but also to tokenize beforehand, and you could imagine combining two columns to embed, or adding filtering here. 

### Event

Each event represents a raw Postgres row change: 

```typescript
interface Event {
  operation: "insert" | "update" | "delete";
  id: number | string;
  columns: (string | null)[];
}
```

### Action

Each action, what we output from a transform, tells puffgres what to do in turbopuffer. Return one of:

```typescript
type Action =
  | {
      type: "upsert";
      id: number | string;
      document: Record<string, unknown>;
      vector?: number[];
      distance_metric?: string;
      schema?: Record<string, unknown>;
    }
  | { type: "delete"; id: number | string }
  | { type: "skip" };
```

- **`upsert`** — write a document to turbopuffer. `vector` and `distance_metric` (`"cosine_distance"` or `"euclidean_squared"`) are required together. `schema` defines attribute types for the namespace (see [turbopuffer docs](https://turbopuffer.com/docs/write#schema)).
- **`delete`** — remove the document with this id.
- **`skip`** — do nothing for this event.

### Example

Here's a complete transform that embeds buyer names and upserts them with cosine distance search:

```typescript
import "../../utils/load-env.ts";
import { createInterface } from "readline";
import { embedBatchZeroEntropy } from "../../utils/embed-zeroentropy.ts";
import { parseRow } from "./schema.ts";

interface Event {
  operation: "insert" | "update" | "delete";
  id: number | string;
  columns: (string | null)[];
}

type Action =
  | {
      type: "upsert";
      id: number | string;
      document: Record<string, unknown>;
      vector?: number[];
      distance_metric?: string;
      schema?: Record<string, unknown>;
    }
  | { type: "delete"; id: number | string }
  | { type: "skip" };

const rl = createInterface({ input: process.stdin });

for await (const line of rl) {
  const input: Event[] = JSON.parse(line);

  const upsertEvents = input.filter((e) => e.operation !== "delete");
  const buyerNames = upsertEvents.map(
    (e) => parseRow(e.columns).buyer_name ?? "",
  );
  const vectors = await embedBatchZeroEntropy(buyerNames);
  const vectorMap = new Map(upsertEvents.map((e, i) => [e.id, vectors[i]]));

  const output: Action[] = input.map((event) => {
    if (event.operation === "delete") {
      return { type: "delete", id: event.id };
    }

    const row = parseRow(event.columns);

    return {
      type: "upsert",
      id: event.id,
      document: {
        buyer_name: row.buyer_name,
      },
      vector: vectorMap.get(event.id)!,
      distance_metric: "cosine_distance",
      schema: {
        buyer_name: { type: "string" },
      },
    };
  });

  process.stdout.write(JSON.stringify(output) + "\n");
}
```

## Applying

Before `puffgres run` will pick up a config, you need to apply it with `puffgres apply`. The run command only loads configs that have already been applied to the state database.

### Checking

Before applying, validate your config and transform with:

```sh
puffgres check              # all configs
puffgres check --name film  # just one
```

`check` regenerates `schema.ts` from the live database, then verifies the referenced table exists, the id column has a unique index, the id type is compatible, and the transform runs successfully on a sample row from the table — pulling a real row through your transform so you catch bugs early. It never writes to the state database, so it's safe to run before `apply` and good to run in CI.
